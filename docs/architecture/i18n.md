# Internationalization (i18n)

How the platform's **instruction language** (the UI + the tutor's
explanations) is structured, and a step-by-step checklist for **adding a new
language**. The *target* language of study stays English and is unaffected by
any of this.

Design rationale and the V2 decisions live in
[Multilingual English Learning](../features/multilingual-english-learning.md);
this document is the operational counterpart.

## Layers

1. **UI strings** — per-language TypeScript catalogs in
   `src/server/i18n/locales/{es,en}.ts`, a `translate()` / `t` helper
   (`src/server/i18n/index.ts`; dot-path keys, `{{param}}` interpolation,
   missing-key fallback to the key), and the `attachLocale` middleware
   (`src/server/i18n/middleware.ts`) that exposes `res.locals.t/locale/htmlLang`
   to every EJS render.
2. **Client strings** — the server injects a curated slice of the catalog into
   the page as `window.__APP_I18N__` (see `getClientCatalog` /
   `getClientCatalogJson` in `i18n/index.ts`, emitted by
   `views/partials/app-shell-close.ejs`); browser bundles read it through
   `src/client/shared/i18n.js`.
3. **Preference** — a per-profile `instruction_language` column
   (`profiles` and `conversations`), collected at onboarding, editable in the
   profile form and the settings toggle, and snapshotted onto each conversation
   at creation.
4. **Tutor / LLM** — language packs
   (`system-prompts/tutor/language-rules/{es,en}.md` +
   `src/server/services/llmTutor/languagePack.ts`) parametrize the tutor system
   prompt and every `tutor/blocks/*.md` document; secondary families
   (quiz-result evaluation, tutor reports, resource-draft authoring, roleplay
   evaluation) are parametrized through the `{{INSTRUCTION_LANGUAGE_NAME}}`
   placeholder.

## Locale resolution

`resolveLocale` (`src/server/i18n/resolve.ts`), first match wins:

1. the active profile's `instruction_language` (authoritative for signed-in
   users), else
2. the explicit switcher cookie `misterf_lang`, else
3. `Accept-Language` negotiated against `supportedLocales`, else
4. `defaultLocale` (`en`).

`?lang=xx` on any page sets the cookie and redirects clean. At signup the
resolved pre-account language seeds the first profile.

## Adding a new instruction language

Worked example: adding Haitian Creole (`ht`). Steps are grouped by layer;
most are mechanical, a few need human translation or a pedagogy decision.

### 1. Register the locale (types + constants)

- `src/server/i18n/index.ts` — add `'ht'` to `supportedLocales`.
- `src/server/profiles/instructionLanguage.ts` — add `'ht'` to
  `instructionLanguages`.
- `src/server/services/llmTutor/languagePack.ts` — extend the
  `InstructionLanguage` type and the `englishNames` map (`ht: 'Haitian
  Creole'`).
- **Friction — the hand-written union.** `'en' | 'es'` is currently repeated
  verbatim across ~8 files (`db/repository.ts`, `services/roleplays.ts`,
  `services/resourceDrafts.ts`, `services/tutorReports.ts`,
  `services/quizzes.ts`, `services/llmTutor/{prompt,index,languagePack}.ts`).
  Before adding a third language, **centralize it**: export a single
  `InstructionLanguage` type and import it everywhere, then widening is a
  one-line change. Until that refactor lands, every occurrence must be widened
  by hand.

### 2. UI catalog

- Copy `src/server/i18n/locales/en.ts` to `ht.ts` and translate every value
  (keep the key structure identical), then register it in the `catalogs` map in
  `i18n/index.ts`.
- The client dictionary (`clientNamespaces`) and `<html lang>` need no change —
  they read whatever locale resolves.

### 3. Database

- Add a migration widening the `CHECK (instruction_language IN (...))`
  constraint on **both** `profiles` and `conversations`. SQLite cannot alter a
  `CHECK` in place, so this is a table-rebuild migration (create new table with
  the widened constraint, copy rows, drop, rename) — follow the existing
  migration style in `src/server/db/migrations.ts`.
- Existing rows and the column default stay `'es'`; no backfill needed.

### 4. Preference UI

- Add the language option to the radio groups in
  `views/profiles-form.ejs` and `views/profile-onboarding.ejs`, and to the
  settings language toggle. Show the option's **endonym** (e.g. `Kreyòl
  ayisyen`) as a literal, like the existing `Español` / `English`.
- Add the language to the public switcher
  (`views/partials/language-switcher.ejs`).

### 5. Tutor language pack

- Create `system-prompts/tutor/language-rules/ht.md` (the injected
  `{{LANGUAGE_RULES}}` fragment).
- Extend every per-language map in `languagePack.ts`:
  `directionOptionsLettered`, `directionOptionsList`, `learnerAudienceClause`,
  `uiPracticeGuideTerm`, `uiResourcesTerm`, and the translation-block
  enumerations (`translationExerciseBlocksInline`,
  `translationExerciseBlockCombinations`, `translationUnionMembers`).
- **Pedagogy decision:** whether the language is monolingual (like `en`, no
  translation scaffolding — empty translation enumerations, translation blocks
  dropped from the block set) or support-language style (like `es`, with
  translate/understand blocks). This choice drives the translation-block maps
  and the block-set selection.
- Block-doc JSDoc (`tutor/blocks/*.md`) is **automatic** — every learner-facing
  field is already parametrized by `{{INSTRUCTION_LANGUAGE_NAME}}`.

### 6. Secondary LLM surfaces

Automatic once the catalog + `englishNames` entry exist: quiz-result
evaluation, tutor reports, resource-draft authoring, and roleplay evaluation
all render through `{{INSTRUCTION_LANGUAGE_NAME}}` and thread the language from
the profile/conversation. No per-prompt edit needed.

### 7. Transactional surfaces (human translation)

- Emails: translate the `email.*` catalog keys.
- Legal pages: translate the full `privacy` / `terms` bodies (`legal.*`).
- Error pages resolve through the catalog automatically.

### 8. Tests

- Extend the golden snapshot / prompt-contract coverage
  (`tests/llmTutor/promptContracts.test.ts`, `tests/server/i18n.test.ts`): no
  unresolved `{{` placeholders in the rendered prompt, invariant tutor-contract
  sections present, and the Spanish output still byte-for-byte unchanged.
- Add a per-view render smoke in the new locale.

### 9. Manual QA

Full walkthrough in the new language (signup → onboarding → tutor session →
quiz → shared resource) plus a Spanish regression pass.

## What's automatic vs. manual

- **Automatic** (reads the resolved locale, no per-language code): locale
  resolution, `<html lang>`, the client dictionary, block-doc JSDoc, and every
  secondary LLM prompt.
- **Manual**: the catalog translation, the DB `CHECK` migration, the tutor
  language-rules fragment + `languagePack` maps, the preference/switcher UI
  options, legal/email bodies, and QA.

## Known residuals (any language)

Not yet routed through the catalog, tracked for follow-up: relative-time
formatting, a few context-less socket edges (pre-auth prompt, the ES–EN
translator, some not-found paths), progress-overview summaries, and stored
default names (`Nueva conversación`, `Perfil principal`).
