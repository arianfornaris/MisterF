# Internationalization (i18n)

How the platform's **instruction language** (the UI + the tutor's
explanations) is structured, and a step-by-step checklist for **adding a new
language**. The *target* language of study stays English and is unaffected by
any of this.

Design rationale and the V2 decisions live in
[Multilingual English Learning](../features/multilingual-english-learning.md);
this document is the operational counterpart.

## The language registry

`src/server/i18n/languages.ts` is the **single source of truth** for every
supported language. One entry per language holds its code, endonym, English
name, `monolingual` flag, UI catalog reference, and tutor language pack. The
`Locale` type, `supportedLocales`, `defaultLocale`, the UI language pickers,
and every parametrized prompt derive from it — there is no hand-written
`'es' | 'en'` union anywhere. Adding a language is one entry here plus its two
content files (see below).

## Layers

1. **UI strings** — per-language TypeScript catalogs in
   `src/server/i18n/locales/{es,en}.ts` (referenced from the registry), a
   `translate()` / `t` helper
   (`src/server/i18n/index.ts`; dot-path keys, `{{param}}` interpolation,
   missing-key fallback to the key), and the `attachLocale` middleware
   (`src/server/i18n/middleware.ts`) that exposes `res.locals.t/locale/htmlLang`
   to every EJS render.
2. **Client strings** — the server injects a curated slice of the catalog into
   the page as `window.__APP_I18N__` (see `getClientCatalog` /
   `getClientCatalogJson` in `i18n/index.ts`, emitted by
   `views/partials/app-shell-close.ejs`); browser bundles read it through
   `src/client/shared/i18n.js`.
3. **Preference** — a per-profile `instruction_language` column
   (`profiles` and `conversations`), collected at onboarding, editable in the
   profile form and the settings toggle, and snapshotted onto each conversation
   at creation.
4. **Tutor / LLM** — language packs
   (`system-prompts/tutor/language-rules/{es,en}.md` +
   `src/server/services/llmTutor/languagePack.ts`) parametrize the tutor system
   prompt and every `tutor/blocks/*.md` document; secondary families
   (quiz-result evaluation, tutor reports, resource-draft authoring, roleplay
   evaluation) are parametrized through the `{{INSTRUCTION_LANGUAGE_NAME}}`
   placeholder.

## Locale resolution

`resolveLocale` (`src/server/i18n/resolve.ts`), first match wins:

1. the active profile's `instruction_language` (authoritative for signed-in
   users), else
2. the explicit switcher cookie `misterf_lang`, else
3. `Accept-Language` negotiated against `supportedLocales`, else
4. `defaultLocale` (`en`).

`?lang=xx` on any page sets the cookie and redirects clean. At signup the
resolved pre-account language seeds the first profile.

## Adding a new instruction language

Worked example: Haitian Creole (`ht`). Three things to author; everything
else derives from the registry and is compiler-checked.

### 1. Content file — UI catalog

Copy `src/server/i18n/locales/en.ts` to `ht.ts` and translate every value
(keep the key structure identical). This includes the transactional copy:
`email.*`, the `legal.*` privacy/terms bodies, and the per-language profile
option descriptions `profiles.langDesc{Form,Onboarding}.ht`.

### 2. Content file — tutor language rules

Create `system-prompts/tutor/language-rules/ht.md` (the `{{LANGUAGE_RULES}}`
fragment injected into the tutor system prompt).

### 3. Registry entry

Add one entry to `languages.ts` importing the new catalog, with the endonym
(`Kreyòl ayisyen`), English name, `monolingual` flag, and the `tutor` pack
(direction-option examples, UI nouns, the translation-block enumerations, and
the conversation-title rule). TypeScript makes the pack **exhaustive** — omit
a field and it won't compile, so the type checker is your checklist.

**Pedagogy decision** captured by the entry: `monolingual: true` (like `en`,
no translation scaffolding — empty translation enumerations, translation
blocks dropped from the block set) or `false` (like `es`, with
translate/understand blocks).

### What updates automatically

- `Locale`, `supportedLocales`, and the catalog map (derived from the
  registry).
- The profile language radios (form, onboarding, settings) and the public
  switcher — they loop `res.locals.languages`, so the option and switcher
  button appear on their own with the endonym.
- `<html lang>`, the client dictionary, and locale resolution.
- The tutor system prompt, block-doc JSDoc, and the secondary LLM families
  (quiz-result evaluation, tutor reports, resource-draft authoring, roleplay
  evaluation) — all parametrized through the registry / `{{INSTRUCTION_LANGUAGE_NAME}}`.
- **The database** — the `instruction_language` allowlist is enforced in
  application code, not by a DB `CHECK` (removed in migration 16), so no
  migration is needed.

### Tests and QA

- Extend the golden snapshot / prompt-contract coverage
  (`tests/llmTutor/promptContracts.test.ts`, `tests/server/i18n.test.ts`): no
  unresolved `{{` placeholders, invariant tutor-contract sections present, and
  Spanish output still byte-for-byte unchanged.
- Manual walkthrough in the new language (signup → onboarding → tutor session →
  quiz → shared resource) plus a Spanish regression pass.

## Known residuals (any language)

Not yet routed through the catalog, tracked for follow-up: relative-time
formatting, a few context-less socket edges (pre-auth prompt, the ES–EN
translator, some not-found paths), progress-overview summaries, and stored
default names (`Nueva conversación`, `Perfil principal`).
