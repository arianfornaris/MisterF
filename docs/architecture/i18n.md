# Internationalization (i18n)

How the platform's **instruction language** (the UI + the tutor's
explanations) is structured, and a step-by-step checklist for **adding a new
language**. The *target* language of study stays English and is unaffected by
any of this.

Design rationale and the V2 decisions live in
[Multilingual English Learning](../features/multilingual-english-learning.md);
this document is the operational counterpart.

## The language registry

`src/server/i18n/languages.ts` is the **single source of truth** for every
supported language. One entry per language holds its code, endonym, English
name, `monolingual` flag, UI catalog reference, and tutor language pack. The
`Locale` type, `supportedLocales`, `defaultLocale`, the UI language pickers,
and every parametrized prompt derive from it — there is no hand-written
`'es' | 'en'` union anywhere. Adding a language is one entry here plus its two
content files (see below).

## Layers

1. **UI strings** — per-language TypeScript catalogs in
   `src/server/i18n/locales/{es,en}.ts` (referenced from the registry), a
   `translate()` / `t` helper
   (`src/server/i18n/index.ts`; dot-path keys, `{{param}}` interpolation,
   missing-key fallback to the key), and the `attachLocale` middleware
   (`src/server/i18n/middleware.ts`) that exposes `res.locals.t/locale/htmlLang`
   to every EJS render.
2. **Client strings** — the server injects a curated slice of the catalog into
   the page as `window.__APP_I18N__` (see `getClientCatalog` /
   `getClientCatalogJson` in `i18n/index.ts`, emitted by
   `views/partials/app-shell-close.ejs`); browser bundles read it through
   `src/client/shared/i18n.js`.
3. **Preference** — a per-profile `instruction_language` column
   (`profiles` and `conversations`), collected at onboarding, editable in the
   profile form and the settings toggle, and snapshotted onto each conversation
   at creation.
4. **Tutor / LLM** — language packs
   (`system-prompts/tutor/language-rules/{es,en}.md` +
   `src/server/services/llmTutor/languagePack.ts`) parametrize the tutor system
   prompt and every `tutor/blocks/*.md` document; secondary families
   (quiz-result evaluation, tutor reports, resource-draft authoring, roleplay
   evaluation) are parametrized through the `{{INSTRUCTION_LANGUAGE_NAME}}`
   placeholder.

## Locale resolution

`resolveLocale` (`src/server/i18n/resolve.ts`), first match wins:

1. the active profile's `instruction_language` (authoritative for signed-in
   users), else
2. the explicit switcher cookie `misterf_lang`, else
3. `Accept-Language` negotiated against `supportedLocales`, else
4. `defaultLocale` (`en`).

`?lang=xx` on any page sets the cookie and redirects clean. At signup the
resolved pre-account language seeds the first profile.

## Adding a new instruction language

Worked example: Haitian Creole (`ht`). Three things to author; everything
else derives from the registry and is compiler-checked.

### 1. Content file — UI catalog

Copy `src/server/i18n/locales/en.ts` to `ht.ts` and translate the values
(keep the key structure identical), including the per-language profile option
descriptions `profiles.langDesc{Form,Onboarding}.ht`. Fallback rules let a
beta ship partial:

- **Server-rendered keys** fall back per-key to the default locale (English)
  when missing — so low-value/long-tail namespaces (`email.*`, `legal.*`
  bodies, `msg.*`, `superadmin.*`) can be omitted for a first pass.
- **Client namespaces** (`chat`, `nav`, `translator`, `clientChat`, `card`,
  `clientMisc`) fall back per *namespace*, not per key — so translate each of
  those **completely or not at all**, or the client shows raw keys.

Status: `ht` is a **full instruction language** on the `v2` branch — the
catalog is complete (every namespace, no English fallback) and the
experimental flag is removed. A fluent-speaker review of the legal and
high-visibility copy is still a recommended (non-blocking) follow-up.

### 2. Content file — tutor language rules

Create `system-prompts/tutor/language-rules/ht.md` (the `{{LANGUAGE_RULES}}`
fragment injected into the tutor system prompt).

### 3. Registry entry

Add one entry to `languages.ts` importing the new catalog. The
`LanguageDefinition` type makes it **exhaustive** — omit a field and it won't
compile, so the type checker is your checklist. The entry holds *everything*
that varies by language, so no other file needs editing:

- `endonym`, `englishName`, `monolingual`, optional `experimental` (a `true`
  value surfaces the beta badge in the profile picker via
  `profiles.experimental`).
- `catalog`: the imported UI catalog.
- `tutor`: the prompt pack — direction-option examples, UI nouns, the
  translation-block enumerations, the conversation-title rule, and
  `includesSpanishTranslationBlocks` (the flag that gates the Spanish
  translate/understand blocks + quiz items; replaces the old `=== 'es'`
  checks).
- `greetings`: the `initial` / `knownVisitor` greeting arrays (were in
  `socket/initialGreetings.ts`).
- `leakagePatterns`: the block-repair leakage regexes for this support
  language (were a `Record` in `blockRepair.ts`).

**Pedagogy decision** captured by `includesSpanishTranslationBlocks` — three
cases:

- `monolingual: true` (like `en`): teach English through English, no
  translation scaffolding. `includesSpanishTranslationBlocks: false`, empty
  translation enumerations; translate/understand blocks dropped from the block
  set.
- Spanish (`es`): `includesSpanishTranslationBlocks: true`; explanations in
  the support language with the `translate_to_english_prompt` and
  `understand_in_spanish_prompt` blocks and quiz items.
- A non-Spanish support language (`ht`): `monolingual: false` (explanations in
  the support language) but `includesSpanishTranslationBlocks: false`, because
  the two translation blocks are Spanish-hardcoded — until a language-specific
  comprehension block or a parametrized `translate_to_english_prompt` exists.

### What updates automatically

- `Locale`, `supportedLocales`, and the catalog map (derived from the
  registry).
- The profile language radios (form, onboarding, settings) and the public
  switcher — they loop `res.locals.languages`, so the option and switcher
  button appear on their own with the endonym.
- `<html lang>`, the client dictionary, and locale resolution.
- The tutor system prompt, block-doc JSDoc, the block set, the quiz protocol,
  and the secondary LLM families (quiz-result evaluation, tutor reports,
  resource-draft authoring, roleplay evaluation) — all parametrized through the
  registry / `{{INSTRUCTION_LANGUAGE_NAME}}` and the tutor pack.
- The pre-message greetings (`pickInitialGreeting` /
  `pickKnownVisitorGreeting`) and the block-repair leakage detection — both
  read their per-language data from the registry entry, so there is no
  separate map to keep in sync.
- **The database** — the `instruction_language` allowlist is enforced in
  application code, not by a DB `CHECK` (removed in migration 16), so no
  migration is needed.

### Tests and QA

- Extend the golden snapshot / prompt-contract coverage
  (`tests/llmTutor/promptContracts.test.ts`, `tests/server/i18n.test.ts`): no
  unresolved `{{` placeholders, invariant tutor-contract sections present, and
  Spanish output still byte-for-byte unchanged.
- Manual walkthrough in the new language (signup → onboarding → tutor session →
  quiz → shared resource) plus a Spanish regression pass.

## Dates, collation, and the locale rule

Every date a user reads goes through `src/server/i18n/dates.ts`:

- `formatRelativeTime(value, locale)` words "3 months ago" from the catalog's
  `common.relativeTime` keys. It never uses `Intl.RelativeTimeFormat`: Node's
  ICU has no Haitian Creole and silently answers in English. The browser twin
  is `src/client/shared/relativeTime.js`; a test keeps their thresholds equal.
- `formatDateTime(value, locale)` (exposed to views as `formatDateTime`) uses
  `Intl` when the registry entry's `dates.intlLocale` is set, and the entry's
  own `monthNames` when it is `null`, as it is for `ht`.
- `compareText(left, right, locale)` sorts titles.

A language `Intl` has no data for must set `dates.intlLocale: null` and supply
month names; adding a language means checking `Intl.DateTimeFormat
.supportedLocalesOf([code])` first.

No locale parameter has a default. `tests/server/localeArchitecture.test.ts`
rejects a literal locale handed to `Intl`, `localeCompare`, `toLocale*String`
or `translate`, and any `Locale = 'xx'` default, outside this module and two
allowlisted files. Messages about a conversation use the conversation's
language; socket messages with no conversation use the profile's, then the
handshake's (`resolveHandshakeLocale`).

## Known residuals (any language)

- Stored AI output (evaluations, summaries, feedback) keeps the language that
  was active when it was generated. That is content, not chrome.
- Default names are stored in the profile's language at creation
  (`profiles.defaultName`, `nav.newConversation`,
  `nav.practiceConversationTitle`); rows created before 2026-09-10 keep
  `Nueva conversación` / `Perfil principal` until renamed.
- The founder-only superadmin page formats in Spanish on purpose.
